# GPU downscaling on Mac — 2026-11-06

Does uploading the codec's native-scale output and resampling with Metal Performance Shaders beat the shipped CoreGraphics resample? Exploratory run on one machine. **See the [iPhone Air follow-up](2026-11-06-gpu-scale-iphone.md):** on device, ImageIO beats TurboJPEG for manga-sized JPEGs too, which reverses the JPEG routing finding below.

Hardware: Apple M4 Max (14 cores), macOS 27.0.1, Release build. libjpeg-turbo 3.1.3, libjxl 0.11.2. The library sources at `8d426fc` were compiled natively for macOS in a temporary SwiftPM package, with `UIImage` shimmed to `NSImage`. Thermal state was nominal at start and end.

## Method

Each pipeline starts from compressed `Data` in memory and ends with an `MTLTexture` ready for sampling (the GPU command buffer has completed). Each case has one untimed warm-up (which also provides the quality readback), then seven timed runs; tables report medians. CPU time is process CPU time, so it includes libjxl worker threads. MPS kernels and the command queue are created once. Destination textures are allocated per run in `.private` storage.

| Pipeline | Decode | Resample | Upload |
|---|---|---|---|
| `current` | `ImageSource.decode(targetSize:)` (ImageIO thumbnail for JPEG; native JXL) | CoreGraphics, inside the library | `makeTexture` at output size |
| `native+CG` | TurboJPEG DCT scaling, or JXL DC/box-filtered output | CoreGraphics high quality | `makeTexture` at output size |
| `native+lanczos` / `native+bilinear` | same as `native+CG` | `MPSImageLanczosScale` / `MPSImageBilinearScale` | `makeTexture` at native size |
| `imageio-subsample+lanczos` | ImageIO with `kCGImageSourceSubsampleFactor` 2/4/8 (JPEG only) | `MPSImageLanczosScale` | native-size ImageIO bitmap copied into a texture |

The fixtures are procedural four-panel pages: a zone plate, a colour gradient, line art and screentone, with light grain. Features scale with page width, so oversized pages behave like higher-resolution scans of the same art. JPEG files are quality 85; JXL files are VarDCT, distance 1, effort 3.

The quality reference is an exact area-average downscale of the uncompressed pixels, in the same gamma-encoded space CG and MPS use. PSNR is computed over colour channels only. Absolute values are low because the zone plate and screentone are deliberately close to the output's Nyquist limit. Compare the rows within a case, not the absolute numbers.

**Harness patch.** `JPEGRegionDecoder.readColorSpace` throws on JPEGs that have no ICC profile: libjpeg-turbo 3.1.3 returns -1 ("No ICC profile data has been extracted"), where its header documents a NULL buffer. In the library, `ImageSource` swallows this error and falls back to a full ImageIO decode. The harness treats "failed and no buffer returned" as "no profile, use sRGB". Without that patch, none of the `native` JPEG rows could run. The library has since been fixed: it accepts only the `TJERR_WARNING` case, and keeps untagged grayscale JPEGs on ImageIO, which treats them as gray gamma 2.2.

## Findings

- **The GPU resample is cheap.** MPS Lanczos takes 1–5 ms wall time, including destination allocation, encoding and waiting; actual GPU execution is 0.5–2.4 ms. CoreGraphics takes 2–57 ms for the same work. The larger native-size upload costs an extra 0.5–1.5 ms.
- **Quality is equal or better.** Against the area-average reference, Lanczos scored 0–5.8 dB higher than CoreGraphics in every case but one. The exception is JXL 11000² → 1023², which goes through the 1/8 DC path: Lanczos scored 0.7 dB lower, and the DC approximation itself limits all pipelines there (17–18 dB). Bilinear is less consistent; it sometimes beats Lanczos on gray JXL and is worse on line art. At 1:1, centre crops of CG and Lanczos output are visually indistinguishable.
- **For large JPEGs, ImageIO decodes faster than TurboJPEG.** On the 11000² JPEG, ImageIO's wall time is more than twice its CPU time, which suggests the hardware decoder. Asking ImageIO for a subsampled decode and resampling on the GPU was the fastest JPEG path at 50 MP and above: 25–40% lower latency and about 75% less CPU time than `current`.
- **For manga-sized JPEGs, TurboJPEG decodes faster.** TurboJPEG decodes the 6.6 MP page at 6/8 scale in about 23 ms, against about 45–57 ms for ImageIO. TurboJPEG DCT scaling plus Lanczos halves `current` (58.6 → 27.8 ms). This depends on the ICC fix above.
- **JXL gains about 8 ms (manga) to 50 ms (11000²) per page.** That's simply the CG resample being removed. libjxl decode time varied by ±10 ms between runs, so treat small JXL differences as noise and rely on the resample-stage column instead.
- **One ImageIO anomaly.** At the 1024 bound, the 5000×10000 JPEG is slower than at 2048 in both ImageIO pipelines (about 100 ms, with CPU time equal to wall time). ImageIO appears to use a software path for subsample factor 8.

## Caveats and next steps

- These are M4 Max numbers. A-series CPUs make CoreGraphics relatively slower and GPUs relatively smaller, and iOS hardware JPEG decoding has its own size thresholds. The JPEG size crossover needs to be measured on the iPad Pro and iPhone before routing decisions are hard-coded.
- The procedural fixtures stress resampling on purpose; real comic pages have less near-Nyquist detail.
- Destination textures are allocated per run. A reader that pools them would save a little more.

## Reproduction

1. Create a SwiftPM package (macOS 14) with the three codec dependencies from `Package.swift`.
2. Add an `ImageIOKit` target containing a copy of `ImageIOKit/`, with `import UIKit` replaced by `import AppKit`, a `typealias UIImage = NSImage` shim and `-enable-testing`.
3. With library sources from before the ICC fix, apply the patch described above.
4. Add an executable target containing [2026-11-06-gpu-scale-probe.swift](2026-11-06-gpu-scale-probe.swift) as `main.swift`.
5. Run `swift build -c release`, then `GPUScaleBench <fixture-dir> [png-output-dir]`. Fixtures are generated on the first run and cached.
