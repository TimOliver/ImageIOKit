# Real JPEG XL comic on the 10.5-inch iPad Pro

Tested on iPadOS 17.7.11 in Release with coverage disabled, using a private 198-image JXL comic sample. This follow-up prioritizes per-page decode latency at ordinary comic dimensions.

The current libjxl 0.11.2 build averaged **162.4 ms** across three sampled 2160×3072 grayscale pages fitted to 1440×2048. The local 0.12.0 build averaged **160.3 ms**: about 1.3% faster, too small to establish a useful improvement in this exploratory run. The large speedup observed on the earlier 11000×11000 photo did not carry over to these pages. Production remains on 0.11.2.

## Inputs and method

The archive contains 246,105,561 compressed JXL image bytes: 187 grayscale pages at 2160×3072, six RGB and three grayscale images at 1350×1920, one grayscale spread at 4320×3072, and one RGB spread at 2700×1920. All entries were inspected for dimensions; six were selected for device timing. These six cover a colour cover, a regular page, the median-size regular page, the largest compressed entry, and both spreads. They are not a random sample or a whole-book latency distribution.

Each timed decode constructs a fresh ImageSource from already-loaded compressed Data and calls `decode(targetSize:)`. There are five repetitions per page at each requested bound, in one process per native library build. The reference decode happens after the batch test, so even the first per-page measurement is not a cold process launch. The two builds use identical Swift source; runtime `JxlDecoderVersion()` reported 11002 and 12000 respectively. The published 0.11.2 and locally compiled 0.12 frameworks may differ in native build settings as well as version.

The six-page batch test repeats each worker count three times, alternating worker-count order. It retains all six output buffers. Per-image batch latency starts when its worker begins processing, excluding earlier waiting behind other pages. Archive extraction, input loading, GPU upload and rendering are outside all original-decode timings. Recorded thermal state remained nominal.

## Per-page decode latency

Times are arithmetic means in milliseconds; the range contains the five measured current-build repetitions. A 2048 bound does not upscale the 1920-pixel cover. File sizes use decimal MB; memory uses MiB (1,048,576 bytes).

| Page | Source → output pixels | JXL MB | 0.11.2 mean (range) ms | Local 0.12 mean ms |
|---|---|---:|---:|---:|
| 000 colour cover | 1350×1920 → 1350×1920 | 0.596 | 121.6 (119.1–127.5) | 119.9 |
| 003 manga | 2160×3072 → 1440×2048 | 1.426 | 160.2 (157.4–165.7) | 159.1 |
| 056 manga (median file size) | 2160×3072 → 1440×2048 | 1.271 | 160.2 (155.7–170.4) | 156.5 |
| 117 manga (largest file) | 2160×3072 → 1440×2048 | 2.020 | 166.8 (163.4–173.3) | 165.2 |
| 012–013 grayscale spread | 4320×3072 → 2048×1456 | 1.863 | 325.4 (323.8–327.8) | 323.7 |
| 012–013 colour spread | 2700×1920 → 2048×1456 | 0.961 | 290.2 (285.3–298.6) | 289.1 |

For preheating, about 0.2 seconds is a useful starting decode budget for a regular page from this sample; spreads needed roughly 0.3 seconds. Starting the next page about 0.5 seconds ahead is a reasonable initial scheduling heuristic, with extra allowance for extraction, app contention and rendering. These samples do not establish a p95 or worst-case deadline.

Reducing the requested bound to 1024 had little effect on regular-page latency. Source decoding still dominates. Current-build results:

| Page | 2048 bound ms | 1024 bound ms |
|---|---:|---:|
| 000 colour cover | 121.6 | 129.1 |
| 003 manga | 160.2 | 151.8 |
| 056 manga (median file size) | 160.2 | 151.3 |
| 117 manga (largest file) | 166.8 | 159.2 |
| 012–013 grayscale spread | 325.4 | 236.6 |
| 012–013 colour spread | 290.2 | 166.3 |

A regular 3072-pixel page requested at 2048 cannot use the factor-2 output filter: that would leave too few pixels. It therefore uses a full native output followed by resizing. A 1024 request can use factor-2 filtering, reducing output memory but still processing full codec detail. None of these requests can use the factor-8 DC preview. The smaller colour cover also takes a small resize cost at 1024 that the 2048 request avoids.

## Concurrency and memory

These are mixed six-page batches containing the two slower spreads, so batch per-page averages differ from the regular-page averages above. Batch seconds are the median of three runs; active per-image latency is the mean across all three runs; peak footprint is the highest sampled process value.

| Native build | Workers | Six-page batch seconds | Active per-image latency ms | Peak process MiB |
|---|---:|---:|---:|---:|
| 0.11.2 | 1 | 1.227 | 212.3 | 127.9 |
| 0.11.2 | 2 | 0.910 | 289.7 | 171.0 |
| 0.11.2 | 3 | 0.923 | 377.6 | 175.8 |
| 0.12.0 | 1 | 1.242 | 214.9 | 128.2 |
| 0.12.0 | 2 | 0.885 | 290.0 | 171.1 |
| 0.12.0 | 3 | 0.915 | 366.9 | 167.3 |

Two workers reduced current-build median batch duration by about 26%. A third offered no useful gain and increased individual decode latency. Prioritize a single urgent page; allow up to two background decodes when throughput is the goal. These measurements do not include competing reader UI work.

The initial regular-page decodes reached about 64–65 MiB process footprint, including the host and input. Repeated decodes reached about 75–76 MiB because a separate 11.25 MiB reference buffer remained alive. These are process measurements, not per-image allocation costs. Footprint is sampled every 5 ms and at completion, so short spikes can be missed. The batch retains 66.4 MiB of output pixels in addition to compressed inputs and codec storage.

## Optional disk cache

The current build encoded the same 2K reference pixels using `PixelBuffer.write(to:as:)`, with the chosen JPEG default of 0.95. Each format has one excluded warm-up and five measured writes/reloads, alternating format order. Writes include encoding, writing and atomic rename, without explicit fsync. Reloads include opening a fresh ImageSource and decoding the complete cache file. Recently written files are likely in the OS filesystem cache; these are warm-filesystem measurements.

| Page | JPEG .95 MB | JPEG write ms | JPEG reload ms | PNG MB | PNG write ms | PNG reload ms |
|---|---:|---:|---:|---:|---:|---:|
| 000 colour cover | 1.048 | 37.2 | 18.4 | 4.483 | 216.1 | 70.4 |
| 003 manga | 1.473 | 42.9 | 21.4 | 2.807 | 126.4 | 45.6 |
| 056 manga (median file size) | 1.273 | 39.1 | 21.0 | 2.429 | 112.2 | 46.5 |
| 117 manga (largest file) | 1.861 | 49.9 | 22.8 | 3.336 | 141.3 | 55.7 |
| 012–013 grayscale spread | 1.037 | 37.4 | 20.1 | 2.506 | 124.4 | 69.5 |
| 012–013 colour spread | 1.064 | 39.4 | 19.8 | 5.173 | 252.5 | 81.8 |

The regular pages reload from JPEG in about 22 ms, approximately 7.5 times faster than their JXL decode in this sample. Cache construction still pays for original decoding plus encoding. Unlike the oversized JPEG sample, JPEG caches here are not consistently smaller than the JXL sources. The unscaled cover grows from 0.596 MB JXL to 1.048 MB JPEG; the median manga page is essentially unchanged at 1.27 MB. This cache trades disk space and encoding work for faster revisits.

PNG reloads matched every reference RGB value on all six opaque pages. JPEG is lossy; the colour illustrations showed larger channel changes than the grayscale pages:

| Page | JPEG RGB MAE / 255 | Maximum channel error / 255 | PSNR dB |
|---|---:|---:|---:|
| 000 colour cover | 3.071 | 156 | 32.01 |
| 003 manga | 0.714 | 9 | 46.27 |
| 056 manga (median file size) | 0.611 | 8 | 47.02 |
| 117 manga (largest file) | 0.896 | 9 | 45.24 |
| 012–013 grayscale spread | 1.038 | 9 | 45.43 |
| 012–013 colour spread | 2.150 | 121 | 35.29 |

All six sampled files returned no reconstructed JPEG data, so the existing JPEG-reconstruction API cannot bypass their JXL decode. The reconstruction result was not timed.

The two native builds produced closely matching but nonidentical 2K pixels: mean absolute RGB differences were 0.14–0.30 out of 255 across these six images, with maximum channel differences of 1–3. These comparisons establish similarity between the tested outputs, not ground-truth codec accuracy.

## Evidence and reproduction

- Both physical-device runs passed their two benchmark tests with zero failures. The normal example app was restored afterward.
- [Raw results](2026-09-27-real-jxl-results.json) preserve every iteration, sampled memory, neutral input labels, dimensions and quality metrics. Comic titles, source filenames, file hashes and artwork are omitted.
- [Standalone probe](2026-09-27-real-jxl-probe.swift) is outside all production/test targets. Copy it into a temporary example test project as `MemoryTrackingTests.swift`; add the six selected files as a `ProbeFixtures` folder resource, named `page000.jxl`, `page003.jxl`, `page056.jxl`, `page117.jxl`, `page012.jxl`, and `page013.jxl`. The last two represent the grayscale and colour spreads respectively.
- Disable the example controller’s delayed decode while benchmarking. The temporary controller kept the iPad awake with `UIApplication.shared.isIdleTimerDisabled = true`.
- Use scheme `ImageIOKitTests`, Release, physical iPad destination, `-parallel-testing-enabled NO`, `-enableCodeCoverage NO`, `ENABLE_TESTABILITY=YES`, and `-only-testing:ImageIOKitTests/MemoryTrackingTests`.
- Device logs, result bundles and exported image attachments are retained locally. Their paths are omitted because they contain private source identifiers. The archive and artwork remain outside the repository.
- The experimental temporary project substitutes `/tmp/ImageIOKit-jxl012-package` for the published dependency, using the local native build described in the [oversized JXL experiment](2026-09-26-jxl-improvements.md).

Only benchmark documentation and the standalone probe are added by this follow-up. Production code and dependency versions are unchanged.
