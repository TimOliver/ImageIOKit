# iPad Pro oversized-image investigation — 2026-09-26

This report records the original implementation. See the [JXL improvement follow-up](2026-09-26-jxl-improvements.md) for the subsequent filtered callback implementation and updated measurements.

Hardware: connected 10.5-inch iPad Pro, iPadOS 17.7.11. The process reports three CPU cores and approximately 4 GiB physical RAM; this is distinct from the user's approximately 2 GB usable process budget. Release build using Xcode 27 beta, current library source at c31afb4 plus deployment/documentation changes. Native library versions: libjpeg-turbo 3.1.3, libjxl 0.11.2, WebP-Cocoa 1.6.1.

## Method

Temporary XCTest harness, separate copy of the example project; example view controller disabled so its delayed image decode cannot contaminate measurements. Six separately loaded, heap-backed compressed Data inputs model archive entries already extracted into memory. Each page gets a new ImageSource. Workers decode disjoint entries concurrently, with a per-page autorelease pool. All six output PixelBuffers stay alive until the batch finishes, modeling a page cache. Archive extraction, GPU uploads, rendering, and input loading are excluded from timed decode work.

One six-page batch per configuration, sequential configurations in one process. This is an exploratory measurement, not a statistically robust benchmark. Thermal state was fair (1) throughout the final matrix. Code coverage is explicitly disabled for the final matrix below. Earlier exploratory passes used coverage; their timing figures are superseded by this table. All 15 final cases passed. The small-bound JXL batch varied from 12.6–14.6 seconds in the earlier pass to 16.4–16.5 seconds in the final pass; these were not cold-start or temperature-controlled repeats, so do not attribute that variation to coverage alone. Apple ImageIO/system allocator caches can persist across configurations; source objects and their image caches are fresh.

Memory is process physical footprint from TASK_VM_INFO, sampled every 5 ms on a separate queue and after each page. Peak includes inputs, outputs, test host and working allocations. Extra peak is peak minus the pre-decode footprint with all compressed inputs loaded. Sampling can miss short spikes, particularly under CPU contention, so these are observed lower bounds, not guaranteed memory ceilings.

The fixture is the repository's ApplePark JPEG stretched to 11000×11000, encoded on the Mac as 8-bit PNG, JPEG quality 85, opaque lossy WebP quality 85, and JXL VarDCT distance 1 / effort 3 (cjxl 0.11.1, no explicit progressive option). All six entries contain the same pixels but separate input allocations. These are synthetic oversized photo fixtures, not six independent comic pages. Progressive JPEG, lossless/alpha WebP, modular/progressive JXL, other ICC profiles, crops and orientations are not covered by this matrix.

The requested 2048 and 1024 bounds yield actual 2047×2047 and 1023×1023 outputs because SoftwareScaler floors floating-point multiplication. Harness checks accept this one-pixel rounding and verify the source dimensions, output dimensions, successful decode and pixel access; it does not establish visual fidelity.

One full 11000×11000 RGBA bitmap is 461.6 MiB. Six retained 2047×2047 outputs total 95.9 MiB; six 1023×1023 outputs total 24.0 MiB. Compressed inputs matter: the six PNG files occupy approximately 521 MiB before decoding.

## Conclusions

- JPEG: three workers provide the best measured batch time (0.48 seconds), with 300.6 MiB total peak process memory.
- Opaque lossy WebP: two workers provide essentially the same throughput as three (2.68 versus 2.61 seconds). Prefer two for this workload; two-worker peak was 158.3 MiB.
- PNG: three workers improve throughput, but preloading six large compressed PNG files dominates the process baseline. Bound archive extraction/prefetch as well as decoding.
- JXL at 2048: the 1375-pixel DC preview is insufficient, so JXLDecoder selects factor 1, produces the full 461.6 MiB RGBA bitmap, then the facade scales it. One, two, and three workers took 32.04, 21.68, and 21.60 seconds, with respective peaks of 763.3, 1366.6, and 1970.0 MiB. Avoid three workers: virtually no throughput benefit over two and very little headroom within a roughly 2 GB process budget. Even two needs substantial headroom for the rest of the app.
- JXL at the smaller bound: more concurrent decoders add memory without improving throughput. The implementation creates a default libjxl thread pool per decoder. Single-page concurrency is preferable in these measurements.
- For single-worker JPEG, PNG, WebP and small-bound JXL, extra observed peak is well below one full RGBA source bitmap. This is consistent with avoiding a retained full-resolution RGBA output, but does not prove that every codec avoids source-dependent working storage or that no brief allocation was missed.

A diagnostic repeat confirmed the 1024-bound path exits on `JXL_DEC_FRAME_PROGRESSION` with factor 8, while the 2048-bound path exits on `JXL_DEC_FULL_IMAGE` with factor 1. Thus the slow small-bound result is observed even when the DC early exit is actually taken.

## Existing suite and compatibility

The unmodified existing Xcode test suite ran on the physical iPad: 143 tests, one failure. The transparent-JXL test passes its direct libjxl pixel checks, then ImageSource initialization fails. Diagnostic rerun shows CGImageSource creation succeeds but CGImageSourceCopyPropertiesAtIndex returns nil for the 29-byte unassociated-alpha synthetic JXL on iPadOS 17.7.11. The public facade currently requires those metadata properties. No production decoder fix was made in this investigation. After the benchmark, the normal example app was restored and all 33 ImageSourceDecodeTests passed on the same iPad against the final iOS 16 deployment settings with coverage disabled.

With Package.swift lowered from iOS 18 to iOS 16, the actual Swift 6 Release package suite passed all 143 tests on an iOS 18.5 simulator. That confirms package build/test compatibility, not runtime behavior on iOS 16. The dependencies' package manifests and arm64 Mach-O minimum versions both specify iOS 16.0 for libjpeg-turbo and libjxl. The project-level 16.4 setting was aligned to its existing 16.0 targets. iOS 15 remains outside this pass. Public format availability still depends on ImageIO; bundling libjxl does not bypass the ImageSource metadata gate.

The existing memory tests are not a substitute for this probe: many sample after decode has returned, and several full-decode performance cases reuse ImageSource instances whose decoded images are cached. They do not establish transient peak usage for fresh concurrent oversized decodes.

Temporary files are not a permanent benchmark suite. Results apply to these fixtures and this device/OS configuration. Decoder internals and OS implementations may behave differently on other inputs.

Fixture generation (run to completion before starting dependent commands):

```sh
magick ImageIOKitTests/SampleImages/ApplePark.jpeg -resize '11000x11000!' -depth 8 large.png
magick large.png -quality 85 large.jpeg
cwebp -quiet -q 85 large.png -o large.webp
cjxl large.png large.jxl -d 1 -e 3 --num_threads=3
```
