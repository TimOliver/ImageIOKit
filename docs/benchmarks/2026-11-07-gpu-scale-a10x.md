# GPU downscaling on the 10.5-inch iPad Pro (A10X) — 2026-11-07

Task 2 of [TASKS.md](../TASKS.md): rerun the iPhone harness on the weakest supported device before treating the JPEG decode routing as settled. Raw output: [results](2026-11-07-gpu-scale-a10x-results.log), [real pages](2026-11-07-gpu-scale-a10x-real.log), [memory](2026-11-07-gpu-scale-a10x-memory.log).

Hardware: connected 10.5-inch iPad Pro (iPad7,4, A10X), iPadOS 17.7.11 (21H461), three CPU cores, approximately 4 GiB physical RAM. Release build via the [harness](harness/README.md), library at the 2026-11-07 merge of the texture-API branch with the JXL metadata branch. Seven iterations per case, medians reported. Thermal state was fair (1) for every case, so margins under about 10% should not be over-read; the orderings below are far outside that.

## The three routing questions

**1. ImageIO is still faster than TurboJPEG at every JPEG size — the iPhone Air result holds, not the M4 Max reversal.** Median decode-stage times, hardware-decoder ImageIO subsample vs TurboJPEG native-scale:

| Fixture, bound 2048 | ImageIO subsample | TurboJPEG native |
|---|---:|---:|
| manga 2160×3072 gray (6.6 MP) | 18.7 ms | 61.6–63.1 ms |
| page 5000×10000 (50 MP) | 47.5 ms | ~335 ms |
| photo 11000×11000 (121 MP) | 94.5 ms | ~700 ms |

The gap (3–7×) is wider than on the iPhone Air. The per-platform routing — ImageIO subsampling on iOS, TurboJPEG only on Mac/Catalyst — needs no device-floor exception.

**2. `makeTexture` still beats `decode(targetSize:)` in every case**, by 10–45% on fixtures and up to 2.3× on real pages, with equal or better PSNR (photo at 2048: 36.5 vs 30.7 dB against ground truth):

| Fixture | Bound | `decode` wall | `makeTexture` wall |
|---|---:|---:|---:|
| photo 11000×11000 | 2048 | 205.9 ms | 143.9 ms |
| photo 11000×11000 | 1024 | 115.9 ms | 101.3 ms |
| page 5000×10000 | 2048 | 97.4 ms | 69.7 ms |
| page 5000×10000 | 1024 | 58.4 ms | 52.8 ms |
| manga gray, rgba8 | 2048 | 69.0 ms | 53.0 ms |
| manga gray, gray8 | 2048 | 59.0 ms | 32.8 ms |
| manga gray, gray8 | 1024 | 25.9 ms | 19.5 ms |

**3. MPS Lanczos costs 2–17 ms of GPU time on this GPU** (1.9 ms for 625×1250→512×1024 up to 16.6 ms for 2750²→2047²; scale-stage wall 3.4–19.2 ms). Even on a nine-year-old GPU the pass costs far less than the CPU resample it replaces: CoreGraphics scaling the same 2750² native decode took 88.9 ms of CPU.

## Real pages (Scott Pilgrim vol. 1, color edition)

Twelve bundled pages: ten 1800×2700 (4.9 MP) single pages and two 3599×2700 double spreads, all color JPEG. Medians of 10 kept iterations per page:

| Page | Screen | Output | `decode(targetSize:)` | `makeTexture` |
|---|---|---|---:|---:|
| Single 1800×2700 | iPhone SE | 750×1125 | 34.5–43.3 ms | 17.7–21.8 ms |
| | Pro Max (1.36× reduction) | 1320×1979 | 123.2–129.8 ms | 55.5–59.5 ms |
| | iPad (full size) | 1800×2700 | 54.6–60.5 ms | 44.1–48.4 ms |
| Spread 3599×2700 | Pro Max | 1320×990 | ~81 ms | 37–45 ms |
| | iPad | 2064×1548 | ~174 ms | 95–101 ms |

The Pro Max row is the striking one: at small reductions the CPU path pays a full decode plus an ImageIO CPU resample, which the three-core A10X feels much more than the iPhone Air did (where the same comparison tied). `makeTexture` moves that resample to the GPU and is 2.2× faster. Only SE-size targets fit a 60 Hz frame budget; full-size iPad pages run about three frames, so background prefetching matters most on this class of device.

## Memory probe

The copy-vs-shared A/B needs the temporary `ImageSource.benchmarkCopyUpload` switch, which is not in the library; both legs therefore ran the shipped shared-storage path and their near-identical numbers confirm only run-to-run noise. Read the columns as the shipped pipeline's footprint and median time:

| Fixture | Bound | Format | Median | Peak above baseline |
|---|---:|---|---:|---:|
| photo 11000×11000 JPEG | 2048 | rgba8 | 148 ms | 57 MB |
| photo 11000×11000 JXL | 2048 | rgba8 | 2.00 s | 180 MB |
| photo 11000×11000 JXL | 1024 | rgba8 | 2.44 s | 148 MB |
| manga gray JPEG | 2048 | rgba8 | 55 ms | 48 MB |
| manga gray JPEG | 2048 | gray8 | 31 ms | 22 MB |
| manga gray JXL | 2048 | gray8 | 145 ms | 19 MB |
| manga gray JXL | 1024 | gray8 | 178 ms | 17 MB |

Two observations. `gray8` halves both time and peak footprint on gray pages, which is the strongest argument yet for the app-side `.gray8` recommendation on old hardware. And JXL's smaller bound is *slower* than the larger one on both fixtures (2.44 s vs 2.00 s; 178 ms vs 145 ms): the larger box-filter factor costs more in callbacks than it saves, which corroborates task 6's finding from the iPhone and Mac — on the A10X the margin is worse.

## Comparison with the iPhone Air

| Case | iPhone Air | A10X | Ratio |
|---|---:|---:|---:|
| photo 2048, `decode` | 91.0 ms | 205.9 ms | 2.3× |
| manga 2048, `decode` | 17.5 ms | 69.0 ms | 3.9× |
| manga 2048, subsample+Lanczos | 8.5 ms | 36.6 ms | 4.3× |

The A10X is 2–4× slower but every ordering from the iPhone write-up survives. The September A10X baselines ([oversized images](2026-09-26-ipad-pro.md), [JXL follow-up](2026-09-26-jxl-improvements.md)) used the same 11000² JXL fixture; today's ~2.0 s decode at the 2048 bound is consistent with the improved filtered-callback implementation measured there.

## Not covered
