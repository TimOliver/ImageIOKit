# GPU downscaling on the 10.5-inch iPad Pro (A10X) — 2026-11-07

Task 2 of [TASKS.md](../TASKS.md): rerun the iPhone harness on the weakest supported device before treating the JPEG decode routing as settled. Raw output: [results](2026-11-07-gpu-scale-a10x-results.log), [real pages](2026-11-07-gpu-scale-a10x-real.log), [memory](2026-11-07-gpu-scale-a10x-memory.log).

Hardware: connected 10.5-inch iPad Pro (iPad7,4, A10X), iPadOS 17.7.11 (21H461), three CPU cores, approximately 4 GiB physical RAM. Release build via the [harness](harness/README.md), library at the 2026-11-07 merge of the texture-API branch with the JXL metadata branch. Seven iterations per case, medians reported. Thermal state was fair (1) for every case, so margins under about 10% should not be over-read; the orderings below are far outside that.

## The three routing questions

**1. ImageIO is still faster than TurboJPEG at every JPEG size — the iPhone Air result holds, not the M4 Max reversal.** Median decode-stage times, hardware-decoder ImageIO subsample vs TurboJPEG native-scale:

| Fixture, bound 2048 | ImageIO subsample | TurboJPEG native |
|---|---:|---:|
| manga 2160×3072 gray (6.6 MP) | 18.7 ms | 61.6–63.1 ms |
| page 5000×10000 (50 MP) | 47.5 ms | ~335 ms |
| photo 11000×11000 (121 MP) | 94.5 ms | ~700 ms |

The gap (3–7×) is wider than on the iPhone Air. The per-platform routing — ImageIO subsampling on iOS, TurboJPEG only on Mac/Catalyst — needs no device-floor exception.

**2. `makeTexture` still beats `decode(targetSize:)` in every case**, by 10–45% on fixtures and up to 2.3× on real pages, with equal or better PSNR (photo at 2048: 36.5 vs 30.7 dB against ground truth):

| Fixture | Bound | `decode` wall | `makeTexture` wall |
|---|---:|---:|---:|
| photo 11000×11000 | 2048 | 205.9 ms | 143.9 ms |
| photo 11000×11000 | 1024 | 115.9 ms | 101.3 ms |
| page 5000×10000 | 2048 | 97.4 ms | 69.7 ms |
| page 5000×10000 | 1024 | 58.4 ms | 52.8 ms |
| manga gray, rgba8 | 2048 | 69.0 ms | 53.0 ms |
| manga gray, gray8 | 2048 | 59.0 ms | 32.8 ms |
| manga gray, gray8 | 1024 | 25.9 ms | 19.5 ms |

**3. MPS Lanczos costs 2–17 ms of GPU time on this GPU** (1.9 ms for 625×1250→512×1024 up to 16.6 ms for 2750²→2047²; scale-stage wall 3.4–19.2 ms). Even on a nine-year-old GPU the pass costs far less than the CPU resample it replaces: CoreGraphics scaling the same 2750² native decode took 88.9 ms of CPU.

## Real pages (Scott Pilgrim vol. 1, color edition)

Twelve bundled pages: ten 1800×2700 (4.9 MP) single pages and two 3599×2700 double spreads, all color JPEG. Medians of 10 kept iterations per page:

| Page | Screen | Output | `decode(targetSize:)` | `makeTexture` |
|---|---|---|---:|---:|
| Single 1800×2700 | iPhone SE | 750×1125 | 34.5–43.3 ms | 17.7–21.8 ms |
| | Pro Max (1.36× reduction) | 1320×1979 | 123.2–129.8 ms | 55.5–59.5 ms |
| | iPad (full size) | 1800×2700 | 54.6–60.5 ms | 44.1–48.4 ms |
| Spread 3599×2700 | Pro Max | 1320×990 | ~81 ms | 37–45 ms |
| | iPad | 2064×1548 | ~174 ms | 95–101 ms |

The Pro Max row is the striking one: at small reductions the CPU path pays a full decode plus an ImageIO CPU resample, which the three-core A10X feels much more than the iPhone Air did (where the same comparison tied). `makeTexture` moves that resample to the GPU and is 2.2× faster. Only SE-size targets fit a 60 Hz frame budget; full-size iPad pages run about three frames, so background prefetching matters most on this class of device.

## Memory probe

In this first pass the copy-vs-shared A/B ran without the `ImageSource.benchmarkCopyUpload` switch, so both legs took the shipped shared-storage path and their near-identical numbers confirm only run-to-run noise (the follow-up below repeats the A/B with the switch patched in; `setup-ios.sh` now does that automatically). Read the columns as the shipped pipeline's footprint and median time:

| Fixture | Bound | Format | Median | Peak above baseline |
|---|---:|---|---:|---:|
| photo 11000×11000 JPEG | 2048 | rgba8 | 148 ms | 57 MB |
| photo 11000×11000 JXL | 2048 | rgba8 | 2.00 s | 180 MB |
| photo 11000×11000 JXL | 1024 | rgba8 | 2.44 s | 148 MB |
| manga gray JPEG | 2048 | rgba8 | 55 ms | 48 MB |
| manga gray JPEG | 2048 | gray8 | 31 ms | 22 MB |
| manga gray JXL | 2048 | gray8 | 145 ms | 19 MB |
| manga gray JXL | 1024 | gray8 | 178 ms | 17 MB |

Two observations. `gray8` halves both time and peak footprint on gray pages, which is the strongest argument yet for the app-side `.gray8` recommendation on old hardware. And JXL's smaller bound is *slower* than the larger one on both fixtures (2.44 s vs 2.00 s; 178 ms vs 145 ms): the larger box-filter factor costs more in callbacks than it saves, which corroborates task 6's finding from the iPhone and Mac — on the A10X the margin is worse.

## Follow-up: JXL matrix (`--only=.jxl`, same day)

Raw output: [2026-11-07-gpu-scale-a10x-jxl.log](2026-11-07-gpu-scale-a10x-jxl.log). Wall-time medians:

| Fixture | Bound | Box filter (`current`) | Native decode + MPS Lanczos | Full-decode PSNR gain |
|---|---:|---:|---:|---:|
| manga gray 2160×3072, rgba8 | 2048 | 206.6 ms | 159.4 ms | +2.4 dB |
| manga gray, gray8 | 2048 | 166.8 ms | 141.4 ms | +2.4 dB |
| manga gray, rgba8 | 1024 | 218.8 ms | 210.2 ms | +2.7 dB |
| photo 11000×11000 | 2048 | 1916.6 ms | 2190.6 ms | +5.8 dB |
| photo 11000×11000 | 1024 | 2378.5 ms | 2388.2 ms | −0.7 dB |

This answers task 6 for the device floor. At manga size the box-filtered thumbnail loses to a full native decode plus GPU resample on both time and quality, as it did on the iPhone Air and the Mac. More broadly, asking libjxl for *any* downsampled output costs more than decoding in full on this device: the manga's half-resolution decode stage took 171–201 ms against 121–133 ms for the full 2160×3072, and the photo's 1024 bound (downsample 8) ran about 0.4 s slower than its 2048 bound (downsample 4). Only the 121 MP fixture still justifies the filter, for memory rather than speed: its boxed decode peaked at 180 MB against a 484 MB full-resolution bitmap. That is the shape of the `estimatedDecodeMemory` switch task 6 proposes. libjxl saturates all three cores throughout (CPU time 2.3–2.9× wall), so JXL pages on this device also contend with any other background decode.

## Follow-up: copy upload vs shared storage, switch patched in (same day)

Raw output: [2026-11-07-gpu-scale-a10x-memory-ab.log](2026-11-07-gpu-scale-a10x-memory-ab.log). `setup-ios.sh` now patches the `benchmarkCopyUpload` switch into its library copy, so the legs genuinely differ. Medians of 7 alternated pairs:

| Fixture, format | Copy ms | Shared ms | Copy peak | Shared peak |
|---|---:|---:|---:|---:|
| photo 11000² JPEG → 2048, rgba8 | 158.7 | 147.5 | 73.8 MB | 57.5 MB |
| page 5000×10000 JPEG → 2048, rgba8 | 74.3 | 71.0 | 32.4 MB | 23.8 MB |
| manga gray JPEG → 2048, rgba8 | 59.5 | 52.0 | 62.3 MB | 48.1 MB |
| manga gray JXL → 2048, rgba8 | 144.4 | 137.6 | 62.3 MB | 37.7 MB |
| manga gray JPEG → 2048, gray8 | 37.8 | 33.8 | 21.6 MB | 21.6 MB |

Shared storage saves 5–15% wall time on the RGBA paths, like the iPhone. Unlike the iPhone — where peaks did not move — it also cuts peak footprint 20–40% here: the copy upload's `replace(region:)` shows up as an extra plateau on this device, worst on the JXL manga (62.3 vs 37.7 MB). The gray8 legs tie on peak and nearly tie on time, since their buffers are a quarter the size. The adopted shared-storage design is most valuable exactly on the hardware with the least memory.

## Follow-up: zoom-tile crops (`--crop`, TASKS item 5 groundwork, same day)

Raw output: [2026-11-07-gpu-scale-a10x-crop.log](2026-11-07-gpu-scale-a10x-crop.log). Centered crops fitted to an iPad-size bound, comparing the shipped TurboJPEG region decode against the full-ImageIO-decode fallback, cold and with the full decode cached:

| Page | Crop | Region decode | Full, cold | Full, cached |
|---|---|---:|---:|---:|
| page 5000×10000 | 1/2 × 1/2 | 316.9 ms | 393.0 ms | 196.9 ms |
| page 5000×10000 | 1/4 × 1/4 | 167.7 ms | 249.0 ms | 34.7 ms |
| manga gray, rgba8 | 1/2 × 1/2 | 38.2 ms | 47.8 ms | 20.3 ms |
| manga gray, gray8 | 1/2 × 1/2 | 59.3 ms | 42.5 ms | 14.9 ms |
| real page 1800×2700 | 1/4 × 1/4 | 7.4 ms | 12.9 ms | 3.0 ms |

Three observations for the `cropRect`-in-`makeTexture` design. TurboJPEG region decode beats a cold full decode everywhere (1.2–1.6×), so it remains the right first tile. Once the purgeable full-decode cache is warm, cached crops win by up to 4.8× (34.7 vs 167.7 ms on the 50 MP page) — but holding that cache is a memory decision, not a speed one: the 50 MP page's full RGBA bitmap is roughly 200 MB, which is exactly what `estimatedDecodeMemory` should gate on a 2 GB-budget device. And the gray8 region decode is slower than its rgba8 twin on this chip (59.3 vs 38.2 ms) while the ImageIO fallback converts to gray faster than either — worth re-checking before routing gray tiles through TurboJPEG.

## Follow-up: subsampled-bitmap diagnostics (`--diag`, same day)

Raw output: [2026-11-07-gpu-scale-a10x-diag.log](2026-11-07-gpu-scale-a10x-diag.log). The layout assumptions behind the texture path hold unchanged on the A10X: ImageIO's subsampled JPEG bitmaps come back page-aligned with tight rows (bytesPerRow = 4×width for color, 1×width for gray, never 64-byte aligned, so no direct linear-texture view), sRGB for color and single-channel GenericGrayGamma2_2 for gray, and pixel-identical to the CoreGraphics baseline (`maxDiffVsCG=0`). Uploading ImageIO's bitmap directly saves only 1–2 ms over rendering first (8.9 vs 10.3 ms on a 30 MB bitmap) while `dataProvider` access itself costs 15.5 ms — the same copy penalty that ruled this out on the iPhone.
